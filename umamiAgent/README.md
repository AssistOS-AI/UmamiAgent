# Umami Agent

`umamiAgent` exposes self-hosted Umami data through controlled Ploinky MCP tools.

## Components

- Ploinky AgentServer serves `/mcp`.
- `mcp-config.json` exposes one tool per allowed Umami operation.
- `tools/umami_tool.mjs` calls Umami's built-in read-only MCP endpoint (`http://127.0.0.1:3000/mcp`) with an internal API key.
- `scripts/umami-bootstrap.mjs` enforces the admin password and the internal API key before Umami starts, and seeds the configured websites once it is healthy.
- The manifest pins an immutable `docker.io/assistos/umami-agent` image containing Umami 3.4.1 and PostgreSQL.

## Umami Stack

`umamiAgent` is the only Ploinky agent in the Umami stack. Its startup supervisor initializes and starts PostgreSQL, runs Umami's database check, bootstraps credentials, starts the Umami app (with `MCP_ENABLED=1`), seeds websites, and then starts Ploinky AgentServer.

The Umami app listens inside the agent container at:

```text
http://127.0.0.1:3000
```

Ploinky exposes the dashboard through the router at:

```text
/base-agent-additional-server/umamiAgent/3000/
```

Inside the container, `umamiAgent` calls Umami at:

```text
http://127.0.0.1:3000
```

The image builds Umami with `BASE_PATH=/base-agent-additional-server/umamiAgent/3000`.
This is a build-time setting; changing an environment variable cannot repair a
root-built Next.js bundle. Startup verifies the image's build metadata and Next
configuration before initializing PostgreSQL.

The source build includes a recorded login cache correction. After successful
authentication, it cancels any older login verification and caches the returned
user before navigating. An earlier authorization failure therefore cannot send
the authenticated browser back to the login page. The build metadata records
the upstream source and the exact applied patch separately.

Icon links and the web manifest use the same compiled publication prefix,
including the manifest's icon resources. They never require Router-root assets.

The agent ingress listens on container port `3000` and restores that fixed path
before forwarding to Next.js on `127.0.0.1:3001`. It accepts only the exact Router
`X-Forwarded-Prefix` when one is supplied. Internal callers without that header
keep using unprefixed `/api/...` and `/script.js` paths on port `3000`. HTML, assets,
API bodies, redirects, and service authentication pass through unchanged; no
root `/_next` route or extra host port is published. A different prefix requires
a matching image rebuild and agent contract update.

The manifest uses Ploinky's isolated per-agent default network. The services in the stack communicate over container loopback, so no shared network or custom network alias is required.

PostgreSQL data persists in the agent root storage at `/root/postgres`, which Ploinky maps to the workspace `.data` area. During a Ploinky replacement the new runtime waits on an exclusive `flock` (`/root/umami-postgres.lock`) until the old runtime exits, so two PostgreSQL servers never share the data directory; Umami is briefly unavailable during that handover while AgentServer already answers readiness. PostgreSQL uses fixed loopback-only credentials (`admin` / `admin` by default, overridable through `POSTGRES_USER` and `POSTGRES_PASSWORD`); on every start the script re-applies them to the existing data directory in single-user mode, so the database stays usable when the Ploinky workspace or its master key is recreated. The app secret is generated by Ploinky through `UMAMI_APP_SECRET`.

The tracker endpoints are public Router routes so anonymous visitors of tracked sites can reach them: `/base-agent-additional-server/umamiAgent/3000/script.js` (GET/HEAD) and `/base-agent-additional-server/umamiAgent/3000/api/send` (`publicProtocol` POST/OPTIONS with CORS). Umami answers `api/send` with a wildcard CORS policy that the Router never relays, so `scripts/umami-ingress.mjs` echoes the caller's exact origin for that path only. Tracking works from the Explorer's own origin and from other websites: the route also declares `publicProtocol.allowHeaders` with `content-type`, `x-umami-website-id`, `x-umami-hostname` and `x-umami-cache`, the request headers the tracker sends and the ingress advertises for that path. The Router admits only names both lists contain, so `manifest-contract.test.mjs` keeps them equal. A Ploinky Router without `allowHeaders` support rejects this manifest. The dashboard and every other path keep the `explorer.access` gate. The settings plugin defaults the public URL to this Router publication on the Explorer's origin.

Website tracking snippets should send browser events directly to the Umami app URL that is reachable by the website. They should not send tracking events to `umamiAgent`.

## IDE Settings Plugin

`IDE-plugins/umami-settings/` contributes the `Umami Settings` settings entry in AchillesIDE; `IDE-plugins/umami-tool-button/` opens the same modal from the file-explorer toolbar, and its `Open Dashboard` button opens the Umami websites page. The settings modal generates an Umami browser tracking script from:

- the public Umami URL, defaulting to `<Explorer origin>/base-agent-additional-server/umamiAgent/3000`;
- the Umami website selected from the Umami MCP website list.

The plugin calls `umami_websites_list` through Ploinky's Router-mediated `/umamiAgent/mcp` endpoint when the modal opens and shows the returned websites in a selector when Umami credentials are configured. The canonical MCP route lets the Router mint the per-tool secure-wire authorization required by AgentServer; do not send MCP calls through the generic additional-server relay. If a new website is added in the Umami dashboard, close and reopen the settings modal to reload the list. Errors from the MCP call are displayed in the modal and logged with `console.error`. Tracking data still goes directly from the website browser to Umami's `/script.js` endpoint, not to MCP.

## MCP Backend

Umami 3.4.1 serves a read-only MCP endpoint at `/mcp` under the publication prefix when `MCP_ENABLED=1`, which the supervisor sets. It accepts account API keys only. The agent's tools call it over container loopback with an internal key; the ingress answers `404` to Router-forwarded requests for it, so it is not reachable from outside the container.

Configuration (Ploinky variables):

- `UMAMI_INTERNAL_KEY_SEED`: generated by Ploinky for this agent. The API key is `umami_` plus the seed; the bootstrap stores its SHA-512 hash in the `api_key` row `b85ae2ea-c3b8-4a5f-b7dd-ffee2254cc88`. No human holds the key.
- `UMAMI_ADMIN_PASSWORD` (optional, any non-empty value): when set, every start resets the `admin` account to this password. Unset, Umami keeps its upstream first-login `admin` / `umami`, so change it after first login on shared deployments.
- `UMAMI_SEED_WEBSITES` (optional): a JSON array of `{"id": "<uuid>", "name": "...", "domain": "..."}`. Each entry is created, updated or verified through Umami's API at start; an id owned by another user stops the stack.
- `UMAMI_BASE_URL`, `UMAMI_DEFAULT_WEBSITE_ID`, `UMAMI_TIMEZONE`, `UMAMI_OUTPUT_DIR`.

Restarting with unchanged configuration makes no writes and logs `no changes; made no writes` for each phase.

The manifest sets `routerAccess.requiredCapability` to `explorer.access`, so the dashboard and `/umamiAgent/mcp` are limited to users holding that capability; other signed-in users are redirected to the user dashboard when they open an HTML page, and API or MCP requests get a JSON 403. The guest settings-plugin route is subject to the same check.

## Exposed Tools

Original tools: `umami_websites_list`, `umami_stats_get`, `umami_pageviews_get`, `umami_metrics_get`, `umami_events_list`, `umami_active_get`, `umami_sessions_get`, `umami_report_generate`.

Added tools, each mapped to one built-in Umami tool: `umami_website_daterange`, `umami_event_stats`, `umami_event_series`, `umami_event_properties`, `umami_session_stats`, `umami_session_get`, `umami_annotations_list`, `umami_segments_list`, `umami_funnels_list`, `umami_funnel_run`, `umami_goals_get`, `umami_journey_run`, `umami_retention_run`, `umami_attribution_run`, `umami_revenue_get`, `umami_performance_get`. The full mapping is in `docs/specs/DS004-umami-agent.md`.

Times are epoch milliseconds (`startAt`, `endAt`) and are converted to ISO 8601 for Umami.

The agent intentionally exposes no Umami write, admin, user, team, website CRUD, or event ingestion operations.
